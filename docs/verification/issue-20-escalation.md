# 改善課題: 保存結果不明時の再送に関する残存指摘

改善課題の作成・編集・完了報告・完了確認は実装済み。通常の動線と、TypeErrorとして届く通信断後の同一body・同一操作IDによる再送を確認した。修正後の全体試験はFront134、Workers145、bootstrap3、Edge21成功。

## 独立した再レビューで再現した未解消点

保存は成功しているが、利用者への応答が中継サーバーのHTML形式502に置換された場合、fetcherはrequestIdのないREQUEST_FAILEDを返す。TaskFormはApiErrorをすべて確定失敗とみなし、最新の保存済み内容へ同じ更新を再適用して保存ボタンを無効化する場合がある。

通常追加、100件目追加、1MiBちょうどの追加、完了報告、確認済み課題の結果変更、上限近辺の編集、完了確認、差戻し、上限近辺の完了確認の9条件を確認し、うち6条件で再送不能を再現した。元の切断6条件と正式回帰25件は成功したが、この結果をもって解決済みとは扱わない。

## 追加修正案

Errorのクラスだけで判断せず、アプリからの確定した業務拒否と、出所・結果を確定できない通信応答を区別する。同じ検証済み入力と操作IDを持つ結果不明の要求だけは、保存済み最新値への新規遷移検査で再送を妨げない。入力を編集した新要求、401/403/404、明示的な409、閲覧専用、100件・1MiBの制約を維持する。

9条件をTypeErrorとHTML502で検証し、確定した業務拒否との対照も追加する。その後全体試験と独立レビューを再実行する。追加修正の許可が得られるまではこのブランチをmainへ統合しない。

## 判断が必要な理由

dev-implの上限であるレビュー2回・high修正1回の後にhigh/spec-complianceが残存したため、追加修正サイクルの判断を求める。機能範囲・本番公開・外部送信の承認を広げる依頼ではない。独立したAI下書きの検証は継続する。
